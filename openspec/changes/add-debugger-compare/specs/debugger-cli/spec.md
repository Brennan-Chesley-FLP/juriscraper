# Debugger CLI Specification

## Purpose

The debugger CLI (`ldd-debug`) provides tools for inspecting, manipulating, and analyzing LocalDevDriver scraper run databases. This enables developers to debug scraper issues, validate changes, and compare continuation behavior against stored results.

## ADDED Requirements

### Requirement: Dry-Run Comparison Command

The system SHALL provide a `compare` command that replays stored responses through modified continuation code and compares the output against stored results.

#### Scenario: Compare continuation output
- **WHEN** `ldd-debug compare <db-path> <continuation>` is executed
- **THEN** the system SHALL load the scraper class from run metadata
- **AND** replay completed requests for the specified continuation
- **AND** capture requests and data that would be generated by the new code
- **AND** compare against stored child requests and results

#### Scenario: Single request comparison
- **WHEN** `--request-id <id>` is specified
- **THEN** only the specified request SHALL be compared
- **AND** this SHALL enable focused debugging of specific cases

#### Scenario: Sample terminal steps
- **WHEN** `--sample <n>` is specified
- **THEN** the system SHALL randomly select `n` terminal requests (requests that produced no child requests, only ParsedData or nothing)
- **AND** compare the full transitive tree from those terminal points

### Requirement: Transitive Child Comparison

The system SHALL compare all transitively generated child requests when comparing continuation output.

#### Scenario: Full downstream tree comparison
- **WHEN** a continuation generates child requests that generate further children
- **THEN** the comparison SHALL include all levels of the request tree
- **AND** differences at any level SHALL be reported

#### Scenario: Request tree structure diff
- **WHEN** the new code generates a different request tree structure
- **THEN** the diff SHALL show:
  - Added requests (in new code but not original)
  - Removed requests (in original but not new code)
  - Modified requests (same URL but different parameters)

### Requirement: Continuation Purity Assumption

The system SHALL assume continuations are pure functions of their input response.

#### Scenario: Stateless replay
- **WHEN** a continuation is replayed
- **THEN** the system SHALL provide only the stored response content and context
- **AND** any undefined behavior from impure continuations SHALL be the scraper author's responsibility

#### Scenario: Context reconstruction
- **WHEN** replaying a continuation
- **THEN** the system SHALL reconstruct context from stored data:
  - `accumulated_data` from `requests.accumulated_data_json`
  - `aux_data` from `requests.aux_data_json`
  - `permanent` from `requests.permanent_json`
  - `current_location` from `requests.current_location`

### Requirement: Request Capture in Dry-Run Mode

The system SHALL capture all request types without executing network calls.

#### Scenario: Capture NavigatingRequest
- **WHEN** a continuation yields `NavigatingRequest`
- **THEN** the DryRunDriver SHALL capture the request details
- **AND** NOT execute any network call

#### Scenario: Capture NonNavigatingRequest
- **WHEN** a continuation yields `NonNavigatingRequest`
- **THEN** the DryRunDriver SHALL capture the request details
- **AND** NOT execute any network call

#### Scenario: Capture ArchiveRequest
- **WHEN** a continuation yields `ArchiveRequest`
- **THEN** the DryRunDriver SHALL capture the request details including `expected_type`
- **AND** NOT execute any network call

### Requirement: Data Extraction Comparison

The system SHALL compare ParsedData output between original and new code using Levenshtein-based pairing.

#### Scenario: Result pairing via Levenshtein distance
- **WHEN** comparing original and new ParsedData yields
- **THEN** the system SHALL pair results by minimum Levenshtein distance of JSON-serialized forms
- **AND** use greedy assignment: pair smallest distance first, remove from consideration, repeat
- **AND** paired results SHALL be compared using exact Python dict comparison

#### Scenario: Identical paired data
- **WHEN** a paired original and new result have identical dict values
- **THEN** the comparison SHALL report the pair as identical

#### Scenario: Changed paired data
- **WHEN** a paired original and new result have differing dict values
- **THEN** the comparison SHALL report field-level differences
- **AND** show old value vs new value for each changed field

#### Scenario: Added data in new code
- **WHEN** new code yields more results than original
- **THEN** unpaired new results SHALL be reported as "added"

#### Scenario: Removed data in new code
- **WHEN** new code yields fewer results than original
- **THEN** unpaired original results SHALL be reported as "removed"

### Requirement: Error Capture During Replay

The system SHALL capture and report errors that occur during continuation replay.

#### Scenario: New code raises exception
- **WHEN** the new continuation code raises an exception
- **AND** the original execution did not produce an error
- **THEN** the comparison SHALL report "error introduced"
- **AND** include the exception type and message

#### Scenario: New code avoids original error
- **WHEN** the original execution produced an error
- **AND** the new code completes successfully
- **THEN** the comparison SHALL report "error resolved"

#### Scenario: Different error types
- **WHEN** both original and new code produce errors
- **AND** the error types or messages differ
- **THEN** the comparison SHALL report the error change

### Requirement: Comparison Output Modes

The system SHALL support multiple output formats for comparison results.

#### Scenario: Summary output mode
- **WHEN** `--output-mode summary` is specified (default)
- **THEN** the output SHALL show aggregate counts:
  - Total requests processed
  - Identical outputs
  - Request tree changes
  - Data changes
  - Errors introduced/resolved

#### Scenario: Detail output mode
- **WHEN** `--output-mode detail` is specified
- **THEN** the output SHALL show per-request comparisons:
  - Request ID and URL
  - Child request diffs (added/removed/modified)
  - Data field diffs
  - Error changes

#### Scenario: JSON output mode
- **WHEN** `--output-mode json` is specified
- **THEN** the output SHALL be machine-readable JSON
- **AND** include all comparison details structured for programmatic consumption

### Requirement: Comparison Filtering Options

The system SHALL support filtering which comparisons to show.

#### Scenario: Show only request changes
- **WHEN** `--show-requests` is specified
- **THEN** only request tree differences SHALL be displayed
- **AND** data comparison details SHALL be omitted

#### Scenario: Show only data changes
- **WHEN** `--show-data` is specified
- **THEN** only data extraction differences SHALL be displayed
- **AND** request tree comparison details SHALL be omitted

#### Scenario: Limit comparison count
- **WHEN** `--limit <n>` is specified
- **THEN** at most `n` requests SHALL be compared
- **AND** the system SHALL report total eligible requests for context
