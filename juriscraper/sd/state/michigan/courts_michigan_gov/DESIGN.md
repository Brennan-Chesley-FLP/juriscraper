# Michigan Courts Scraper Design

## Site Overview

- **Base URL**: https://www.courts.michigan.gov/case-search/
- **Backing technology**: ASP.NET / Episerver SPA, fronted by Cloudflare,
  with hCaptcha (sitekey `9bf9cc63-9d2e-4f54-98f8-8d3063233b9c`) gating
  the case-detail JSON endpoints.
- **Requires Playwright?** Mixed:
  - **Listing / search endpoints** — plain HTTP works, no captcha.
  - **Per-case detail JSON endpoints** — require an hCaptcha JWT in the
    `captchatoken` header. The token is generated by the SPA on each
    navigation. Direct curl returns
    `{"error":"Captcha validation failed."}`.
- **Document downloads (PDFs)** — direct, no captcha.

The user-facing site terms ("Bulk data downloads … prohibited") apply
to redistribution; the JSON endpoints are publicly accessible.

## Courts Covered

| Site ID            | Display Name           | CourtListener ID |
|--------------------|------------------------|------------------|
| `Court Of Appeals` | Michigan Court of Appeals | `michctapp`   |
| `Supreme Court`    | Michigan Supreme Court | `mich`           |
| `Court Of Claims`  | Michigan Court of Claims | *not in courts_db* (skipped — trial-level court bundled into the appellate search UI) |
| `COA and MSC`      | Combined COA + MSC search | (search-only convenience option) |

The site also has a **Lower Court** facet listing every Michigan trial
court (circuit, probate, juvenile, district) plus admin agencies (MERC,
MESC, PSC, LARA…). These are surfaced as the originating court of an
appellate case but are not target courts for this scraper.

## Search Capabilities

| Mode | Endpoint | Captcha | Useful for |
|------|----------|---------|-----------|
| Listing (cases, opinions, orders) | `GET /case-search/?…&expand=*&currentPageUrl=%2Fcase-search%2F` | No | Date-ordered enumeration |
| Single-case lookup | `GET /api/CaseSearch/AdvancedSearchCaseDetails?aCaseId={id}` | No | Direct lookup by site case ID |
| Case detail (full record) | `GET /c/courts/{coa,msc,coc}casedetaildata/{id}` | **Yes** (JWT in `captchatoken` header) | Parties, dockets, attorneys, judges |
| Document download | `GET /4989b8/siteassets/...pdf` | No | Opinion/order PDFs |

### Listing API details

URL pattern (works directly):

```
https://www.courts.michigan.gov/case-search/
  ?page=1
  &resultType=cases            # or "opinions" / "orders"
  &sortOrder=Newest            # or A-Z, Z-A, Oldest, Relevance
  &pageSize=100                # max 100 (UI options 10/25/50/100)
  &aAppellateCourt=Court+Of+Appeals  # or "Supreme Court", "Court Of Claims", "COA and MSC"
  &aPartyName=...              # optional filters
  &aCaseId=380502
  &aBarNumber=...
  &aAttorneyName=...
  &aLowerCourt=...             # exact uppercase trial-court name
  &aOpenCasesOnly=true
  &expand=*
  &currentPageUrl=%2Fcase-search%2F
```

The response is a JSON Episerver page object whose `caseSearchResults`
field contains three result containers — `caseDetailResults`,
`opinionResults`, `orderResults`. Each has the same shape:

```json
{
  "currentPage": 1,
  "pageSize": 100,
  "totalPages": 49,
  "totalResults": 4848,
  "hasMoreResults": true,
  "selectedSortOption": "Newest",
  "sortByOptions": ["Relevance", "A-Z", "Z-A", "Newest", "Oldest"],
  "facets": [...],
  "searchItems": [...]
}
```

**No date-range filter exists.** `aFilingDate*` / `aDate*` / `dateFrom`
etc. are silently ignored. Date-bounded scraping must walk
`sortOrder=Newest` page-by-page and stop when the oldest item on a page
falls before the desired window's start.

**Caps & quirks:**
- `pageSize` capped at 100. Larger values are silently clamped to 10.
- The legacy `/api/CaseSearch/AdvancedSearchCaseDetails` endpoint exists
  but does **not** honour `page=`/`pageSize=` parameters — pagination
  must go through the SSR endpoint above.
- Result count is uncapped; total can exceed 290k for COA, 79k opinions,
  217k orders.

### `searchItem` schema (cases)

Most useful fields per item:

| Field | Type | Notes |
|-------|------|-------|
| `caseUrl` | `str` | e.g. `/c/courts/coa/case/380502` |
| `courtOfAppealsCaseNumber` | `int` | Numeric COA case ID |
| `supremeCourtCaseNumber` | `int` | Numeric MSC case ID |
| `courtOfClaimsCaseNumber` | `str` | `YY-NNNNNN-XX` form, e.g. `26-000087-MZ` |
| `title` | `str` | Case caption |
| `filingDate` | ISO string | UTC offset present |
| `courts` | `list[str]` | Originating trial court(s) |
| `decision` | `str \| None` | Set when item is an opinion result |
| `documentUrl` | `str \| None` | Direct PDF path for opinions/orders |
| `hasOpinions`, `hasOrders` | `bool` | Whether the case has linked docs |
| `isFinalOpinion`, `isPublished` | `bool \| None` | Opinion classification |
| `courtOfAppealsCaseStatus` / `supremeCourtCaseStatus` | `str` | Open / Concluded / etc. |

### Case detail JSON (captcha-gated)

Endpoints (one per court system):
- `/c/courts/getcourtofappealscasedetaildata/{coaCaseId}`
- `/c/courts/getmichigansupremecourtcasedetaildata/{mscCaseId}`
- `/c/courts/getcourtofclaimscasedetaildata/{cocCaseId}` (e.g. `26-000087`,
  no trailing `-MZ` suffix)

Returns ~60 fields covering all three case-system views (COA / MSC / COC)
of a single matter, plus dockets, parties, judges, judgments, opinions,
orders, briefs, document references, and consolidations.

**Notable structural fields:**

- `dockets[]` — register of actions; each entry has `eventNumber`,
  `eventDate`, `eventDescription`, `eventType`, `docketType`, plus
  optional embedded `documents[]` and `episerverDocuments[]` arrays for
  attached PDFs. Court-specific subtypes (`supreme-court-motion`,
  `judgment`, `notice-of-transfer-coc`, …) carry extra fields like
  `partyNumber`, `serviceDate`, `answerDue`, `selfRepresentedParty`.
- `courtOfAppealsParties[]`, `supremeCourtParties[]`, `courtOfClaimsParties[]`
  — each party has `name`, `connections[]` (PL/DF/AT/AE codes),
  `connectionsValue` ("Plaintiff - Appellant"), and `attorneys[]`
  (each with `name`, `pNumber` (P-number / bar number), `appointType`).
- `judgments[]` — references the originating trial court ruling
  (`trialCourtName`, `trialCourtCaseNumber`, `trialCourtJudgeName`,
  `caseType`).
- `judges[]` — list of trial court judges (strings).
- `caseTypes[]` — appellate case-type strings.
- `consolidatedCases[]`, `relatedCourtOfAppealsCaseNumbers`,
  `releatedSupremeCourtCaseNumbers` (sic — typo in the API),
  `uniqueCourtOfAppealsCaseNumbers`, etc. — case-relationship metadata.
- Document links inside dockets use one of two URL forms:
  - `documents[].fileUrl` — relative path under `/4989b8/siteassets/...`
    served by Cloudflare (no captcha required).
  - `documents[].fileName` only (no `fileUrl`) — older COC dockets;
    no public download.

## Data Available

### Case Summary (from listing API; no captcha)
- docket id (numeric COA / MSC)
- title (case caption)
- filing date
- originating trial court(s)
- case URL
- has-opinions / has-orders flags
- COA / MSC / COC status strings
- case type list (categories) — sometimes populated, often null

### Opinion document (from `resultType=opinions`)
- documentUrl (PDF)
- decision text (e.g. "Affirmed But Remanded")
- isFinalOpinion, isPublished flags
- title formatted as `COA {id} {caption} Opinion - Per Curiam - Unpublished MM/DD/YYYY`

### Order document (from `resultType=orders`)
- documentUrl (PDF)
- title (the underlying case caption)

### Case detail (full — captcha-gated, IN_DEVELOPMENT)
- All summary fields plus dockets, parties, attorneys, judges,
  judgments, opinion/order/brief docket subsets, consolidations,
  related cases.

## Email Notifications
The site has a `/newsroom-social-media/subscribe/` page covering blog and
news subscriptions, but **no per-case alerts** are exposed in the public
case-search UI. (Contrast with appellate sites in OR / NY which expose
email-on-docket-change.)

## Oral Arguments Calendar
Court livestreams are surfaced at `/court-livestream/`, but no
date-searchable oral arguments calendar / schedule is exposed in the
public case-search interface. Hearings appear in the per-case docket as
`Scheduled` event types.

## Bot Protection Notes

- **hCaptcha** (sitekey `9bf9cc63-9d2e-4f54-98f8-8d3063233b9c`) gates the
  per-case JSON endpoints. The token is supplied as a JWT in the
  `captchatoken` request header; tokens are issued per page-load by the
  SPA via `api.hcaptcha.com/getcaptcha/...`.
- Listing endpoints are *not* captcha-gated even though the SPA always
  attaches an empty `captchatoken: ` header.
- Cloudflare fronts everything but does not present an interstitial to
  ordinary curl requests.
- PDF downloads under `/4989b8/siteassets/...` and `/498972/...`,
  `/4989ad/...` are direct (the leading-segment hash is a stable CDN
  prefix, not a session token).

## Scraper Architecture

This scraper is structured to do as much as possible *without* invoking
Playwright/hCaptcha. The captcha-protected case-detail step is left for
a future enhancement; v1 yields case stubs from the listing API.

### Entry points

| Method | Param type | Purpose |
|--------|-----------|---------|
| `get_coa_dockets_by_date` | `DateRange` | Walk `aAppellateCourt=Court+Of+Appeals` newest-first; stop when filing date < `start`. |
| `get_msc_dockets_by_date` | `DateRange` | Same flow for `aAppellateCourt=Supreme+Court`. |
| `fetch_coa_docket` | `SpeculativeRange` | Speculative single-case fetch by COA ID. |
| `fetch_msc_docket` | `SpeculativeRange` | Speculative single-case fetch by MSC ID. |

Listing requests are `nonnavigating=True` HTTP JSON calls. Pagination
proceeds with `deduplication_key=SkipDeduplicationCheck()` for
page-N requests, while individual case yields use the case URL as
`deduplication_key` so repeat calls (e.g. across COA + MSC searches that
share a matter) collapse to one record.

### Step functions

```
get_*_dockets_by_date  -> parse_listing_page  -> (yield Docket per item)
                                              -> next-page Request (if dates still inside window)

fetch_*_docket         -> parse_single_case   -> (yield Docket)
```

Both flows yield `MichDocket` (one `ScrapedData` model with all
court-shared fields). Court-specific fields (e.g. `coa_status`,
`msc_status`) are nullable.

### Models

- `MichDocket` — main output; one record per (court_id, docket_id)
  combination.
- `MichTrialCourtRef` — embedded list for related trial-court entries
  (one matter can sit on top of multiple lower courts).
- `MichSearchHit` — internal helper to type-check the listing JSON
  before building the docket; inlined into the parser, not yielded.
- (Reserved for future captcha-gated detail step:
  `MichDocketEntry`, `MichParty`, `MichAttorney`, `MichJudgment`,
  `MichDocument`.)

### Why no full case-detail step yet?

hCaptcha automation is non-trivial: tokens are short-lived, generated
per page-load via `api.hcaptcha.com`, attached as a custom
`captchatoken` JWT header. kent's `HCAP_HANDLER` driver requirement
covers visible challenge widgets (`div.h-captcha`); the Michigan SPA
uses an *invisible* execute-mode hCaptcha embedded in the SPA's network
layer, which would need a tailored Playwright step. That work is
deferred — the listing API still yields the most operationally
valuable fields (docket id, caption, filing date, originating court,
status, has-opinions/has-orders flags) without it.
